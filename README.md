# B站稍后再看排序

用于 Microsoft Edge / Chrome 的 Manifest V3 扩展，在 B 站原生「稍后再看」页面对**全部**视频按发布时间、视频总时长排序。保留 B 站原生卡片、交互和排版，不创建第二套视频列表。

## v0.7.0：默认排序与页面打开时预加载

1. **每次打开或刷新网页都显示「默认」**，保持 B 站的原生顺序。旧版保留上一次排序选择的行为已移除，不再读写本地 `wl-sorter-mode`。
2. 下拉菜单原先的「B站默认顺序」改为简短的 **「默认」**。
3. **网页打开时就提前获取全量排序数据**：`src/preload.js` 在 `document_start` 开始请求完整 API 元数据；无需等待用户点击排序。
4. **网页渲染出原生列表后自动进行后台预加载**：MAIN-world 桥通过 Vue 3 / Pinia 的 `list` store 调用 B 站自带的 `loadMoreWatchlaterList`，从初始 20 条逐批补齐到当前 `totalCount`（此前用户页面为 424 条）。
5. 这两项工作并行执行；**仅预加载，不重排列表**。用户点击发布时间或时长排序时，复用已预加载的数据，校验原生条目与完整 API 对应后一次性更新 `watchlaterList`。
6. 选择「默认」可以切回原生接口顺序。即使当前排序模式不是默认，网页刷新后也始终重新以默认模式打开。
7. 没有增加额外按钮或进度面板；只有原来的排序下拉框，失败时才显示错误信息。

### 速度与行为

如果网页打开期间两项预加载均已完成，之后切换排序只需计算和修改本地 Pinia 列表，通常比原来的首次点击后逐批加载快得多。

**不能保证页面刚开始加载就完全零等待。** 若用户在预加载尚未完成时立即点击排序，仍需等待剩余的原生加载过程。预加载调用 B 站自身接口，第一次打开时会产生额外的网络请求和视频卡片渲染，可能增加页面初始化的资源开销。这是将排序等待前移到网页打开期间的代价。

不调用滚动 API，不自动刷新网页，不创建替代卡片，也不改变 B 站服务器端顺序。加载完整后才认定全量排序成功；如果 Pinia 列表不足或身份无法匹配，会明确显示「全量排序失败」。

**实际 Edge / B 站登录页面尚未完成端到端验证。** 目前已通过模拟 Pinia 的 20→424 记录补齐、默认顺序保持、模式切换及异步加载测试。原生内部 API 改版可能需要适配。

## 安装与更新（Edge）

1. 从 [GitHub 仓库](https://github.com/PyRookie1/bilibili-watchlater-sorter) 选择 **Code → Download ZIP**，解压并覆盖本地扩展目录。
2. 在 Edge 地址栏打开 `edge://extensions`。
3. 找到扩展，点击「重新加载」。
4. 刷新 [B站稍后再看](https://www.bilibili.com/watchlater/list#/list)，下拉框应显示「默认」。等待页面完成打开，再选择发布时间或总时长排序。

支持：

- 默认
- 发布时间：最新优先／最早优先
- 总时长：短到长／长到短

## 开发

Node.js 20+，运行：

```bash
npm test
```

主要文件：

- `src/preload.js`：页面打开初期启动完整 API 数据请求。
- `src/content.js`：默认模式下拉框、结果缓存、用户选择事件。
- `src/native-intercept.js`：预加载与排序的 MAIN-world 消息队列。
- `src/full-native.js`：定位 Pinia `list` store、原生预加载与全量排序。
- `src/api.js`、`src/background.js`、`src/page-bridge.js`：全量 API 数据和备用读取通道。
- `test/`：排序、预加载、接口完整性及消息通信测试。

## 隐私

使用 B 站已有登录状态访问其接口，不直接读取 Cookie 值，不上传观看列表至第三方服务；默认和排序选择不再持久化。
